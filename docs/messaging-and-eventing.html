The Dispatch Office

Messaging and eventing are not the same thing. This build makes the difference visible on one broker, with one programming interface, and one line of configuration between them.

The distinction

One docket, or a carbon copy

A command is a docket handed to one clerk. Somebody has to do the work, and it must not be done twice.

An event is a memo run off on carbon paper. Every desk that cares gets its own copy, and the sender never learns who read it.

In JetStream both use the same streams and the same calls. The only thing that differs is whether consumers share a durable name.

Messaging

A second worker splits the load.

Both workers ask for order-worker. The server hands each command to exactly one of them.

Eventing

A second subscriber adds a reaction.

order-notifier and order-audit each keep their own position. Both see every event.

If you cannot say which of the two a new subject is, it is a command.

The four things that are easy to get wrong

Correctness, not just plumbing

Transactional outbox

Never publish inside the operation that writes state

The order row and the outgoing message commit together. Publishing directly leaves a window where the order exists and the message is gone, with nothing left to prove it was ever meant to be sent.

The row is marked published only after the broker acknowledges it. Marking first would recreate the same hole.

Idempotency

Dedupe on the business key

On order_id, not the message id. Message ids only catch broker redeliveries; the order id also catches a client submitting the same order twice, which is the duplicate people actually hit.

The claim is released when processing fails. Claiming it up front and never releasing turns a retry into a "duplicate" and loses the message precisely because you tried to be safe.

Retry, then dead-letter

Fail without jamming the queue

Three attempts with a delayed negative acknowledgement, then the message moves to its own stream. A message that can never succeed would otherwise be redelivered forever, with everything behind it waiting.

Distributed tracing

Give back what decoupling takes away

The World Wide Web Consortium traceparent rides in NATS headers, so one trace covers the incoming request, the broker hop and every subscriber. Without it each service produces its own disconnected trace and the one question worth asking — what did this request cause? — has no answer.

The four gaps, since fixed

The trace survives the outbox

Was: the chain broke where it became durable

The trace context now travels inside the envelope, and the envelope is already stored as JavaScript Object Notation in the outbox row — so the context is still there minutes later when the relay picks it up. One field, no new column. A trace now starts at the incoming request:

gateway accept → outbox-relay → worker → subscribers

The relay is its own process

Was: a background task inside the gateway

Running a second gateway for request throughput used to start a second relay whether you wanted one or not. Separated, each scales for its own reason — and more than one copy was always safe, because FOR UPDATE SKIP LOCKED makes them claim different rows.

The dead-letter queue can be drained

Was: messages parked with no way back

DevReplay.cmd moves dead letters back onto the queue, with --dry-run to look first. Deliberately a one-shot tool, not a service: a message is dead-lettered because it kept failing, so replaying on a timer loops forever while looking like progress. Replay is a decision a person makes after fixing something.

Messages carry a schema version

Was: a decode failure was the only signal

A stream holds messages for as long as its retention says, so a deploy puts two payload shapes in flight at once. Every envelope now declares its version; a consumer meeting an unknown one dead-letters it rather than guessing. Additive changes keep the version, anything that could break a reader increments it.
