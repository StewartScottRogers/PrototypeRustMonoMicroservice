The Dispatch Office

Messaging and eventing are not the same thing. This build makes the difference visible on one broker, with one programming interface, and one line of configuration between them.

The distinction

Point-to-point delivery compared with publish-subscribe

A command instructs a single recipient to perform work. Exactly one consumer must act on it, and acting twice is a defect. This is the point-to-point channel.

An event states that something has happened. Every interested subscriber receives its own copy, and the publisher neither knows nor depends upon which subscribers consume it. This is the publish-subscribe channel.

In NATS JetStream both are expressed with the same streams and the same client calls. The sole distinction is whether the consumers share a durable name, which is determined by the consumer configuration.

Messaging

A second worker divides the load.

Both replicas request the durable consumer order-worker, so the server delivers each command to exactly one of them — the same arrangement as a queue group.

Eventing

A second subscriber adds a reaction without removing one.

order-notifier and order-audit each maintain an independent position in the stream, so both observe every event.

Where the classification of a new subject is uncertain, treat it as a command. Performing work twice is a more serious fault than declining to broadcast a fact.

The route

What a single order actually does

Nine containers. The order is committed to Postgres with its outgoing message in one transaction, relayed to the broker, worked once, and then announced to anyone listening.

The four things that are easy to get wrong

Four properties that are commonly implemented incorrectly

Transactional outbox

A message is never published from within the operation that writes state

The order row and the outgoing message are committed in a single database transaction, following the transactional outbox pattern. Publishing directly from the request handler would leave an interval in which the order has been committed and the message lost, with no remaining record that it was ever intended to be sent.

The row is marked as published only after the broker has acknowledged receipt. Marking it beforehand would reintroduce the same interval.

Idempotency

Duplicates are detected by business key, not by message identifier

Detection is performed on order_id rather than the message identifier, making this an idempotent consumer. A message identifier detects only redelivery by the broker; the business key additionally detects a client submitting the same order twice, which is the case encountered more often. Delivery is at least once, so duplicates are a normal operating condition rather than a fault.

The claim is released when processing fails. Retaining it would cause a subsequent retry to be classified as a duplicate, discarding the message as a direct consequence of the precaution intended to protect it.

Retry, then dead-letter

Failure must not obstruct the queue

Three delivery attempts are made, each followed by a delayed negative acknowledgement, after which the message is moved to a dedicated stream — a dead letter channel. A message that can never be processed successfully would otherwise be redelivered indefinitely while every message behind it waits.

Distributed tracing

Restoring the causal record that decoupling removes

The World Wide Web Consortium Trace Context traceparent header is carried in the NATS message headers, so a single trace spans the incoming request, the broker hop and every subscriber. Without it each service emits an unconnected trace, and the question that matters — what did this request cause — cannot be answered.

Closed

Four defects previously identified, now resolved

The trace survives the outbox

Was: the chain broke where it became durable

The trace context is now carried within the envelope, and the envelope is already stored as JavaScript Object Notation in the outbox row. The context therefore remains available minutes later when the relay reads the row: one additional field, and no additional column. A trace consequently begins at the incoming request:

gateway accept → outbox-relay → worker → subscribers

The relay is its own process

Was: a background task inside the gateway

Running a second gateway for request throughput previously started a second relay irrespective of whether one was required. As separate processes each scales for its own reason, and running more than one relay has always been safe because FOR UPDATE SKIP LOCKED causes each to claim a disjoint set of rows.

The dead-letter queue can be drained

Was: messages parked with no way back

DevReplay.cmd returns dead letters to the queue, with --dry-run available to inspect them first. It is deliberately a single-shot tool rather than a service: a message is dead-lettered because it has repeatedly failed, so replaying it on a timer would loop indefinitely while presenting the appearance of progress. Replay is a decision taken by an operator after the underlying cause has been corrected.

Messages carry a schema version

Was: a decode failure was the only signal

A stream retains messages for the duration of its retention policy, so a deployment places two payload shapes in flight simultaneously. Every envelope now declares its version, and a consumer encountering an unrecognised version dead-letters the message rather than inferring a shape. Additive changes retain the version; any change capable of breaking an existing reader increments it. Consumers are written as tolerant readers and ignore fields they do not recognise.

Enforcement

The gates are armed

The repository is public and the branch protection ruleset is active on master. Three aggregate checks are required, and a pull request failing any of them cannot be merged.

Only the aggregate checks are named as required, deliberately. A path-filtered job that does not run reports no status at all, and a required check that never reports leaves a pull request pending indefinitely. Each aggregate job runs unconditionally and fails unless every job it depends on either succeeded or was skipped.

The policy is held in version control at .github/rulesets/master.json and applied by .github/scripts/arm-gates.sh, so the configuration is reviewable in a pull request rather than existing only in the settings of the hosting service. See the documentation on rulesets.

Two capabilities became available at the same time, both having previously been refused on a private repository owned by a personal account: build provenance attestation, and CodeQL analysis. Both are now running.
